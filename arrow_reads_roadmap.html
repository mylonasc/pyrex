Arrow Buffer Reads Roadmap

The parent request is #31. ABR identifiers are stable feature names, not release-version promises. Priority is a delivery order: P0 first, then P1, then P2. Dependencies are explicit delivery/validation gates and are also recorded with GitHub’s native blocked-by and sub-issue relationships.

Delivered baseline

Through 0.7.1, native Arrow C Streams already support lazy bounded batches, full/prefix/range scans, owned binary output, named column families, shared pinned snapshots and committed-state TransactionDB reads. Existing iterator APIs remain supported. multi_get / multi_get_cf return Python lists; they are not an Arrow point-materialization API. TransactionDB scans observe committed state, not transaction-local read-your-writes.

The original design text and unchecked boxes in #31 are historical, not a current feature-availability matrix. These follow-ups cover remaining work.

Why ABR-01 first

Before tuning buffer builders or introducing new streaming sources, measure what the current producer emits, what it allocates, how long native phases take, and what consumers retain. The highest-priority feature adds that observability without changing the default path’s timing collection or requiring PyArrow/Polars in core PyRex. See Batched Arrow Scans for its public collect_metrics=True / ArrowScan.stats contract.

ABR-01 does not replace the existing benchmark. ABR-02 adds an isolated mode and uses ABR-01 counters for fresh-process resource experiments; see Isolated Arrow Benchmarks (ABR-02). ABR-03 adds an independent, atomic cancellation request; existing close() remains the synchronous resource-release API.

Scope boundaries

Every feature retains binary schema/ordering, shared-horizon validation, owned-output lifetimes and explicit error handling. Graph predicates, payload decoding, temporal publication and reasoning remain application responsibilities; raw KV Arrow output is not a decoded graph relation.

Optional optimizations are adopted only with correctness tests and measured benefits. No batch-cap or buffer-counter result is a whole-process RSS bound.
