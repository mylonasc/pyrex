Batched Arrow Scans

Native, columnar reads complement write_columnar_batch(): scan_arrow() iterates RocksDB in C++ and packs raw key/value bytes into Arrow binary columns. Python only sees one Arrow stream per scan instead of one bytes object per record. Consume the stream with any Arrow C Stream client (PyArrow, Polars, DataFusion) without per-row Python conversion.

Quick start:

import pyarrow as pa
import pyrex

db = pyrex.PyRocksDB("/tmp/sensors")
reader = pa.RecordBatchReader.from_stream(db.scan_arrow(prefix=b"sensor/"))
table = reader.read_all()          # struct<key: binary, value: binary>

A scan is lazy and bounded-memory: each get_next gathers at most batch_size rows or max_batch_bytes payload bytes into freshly owned Arrow buffers. Already exported batches stay valid after iterator advancement, stream release, and even database closure.

Scan bounds

  • prefix selects keys starting with the prefix. b""/None = all keys.

  • start is inclusive, stop is exclusive; both are pushed down to RocksDB via iterate_upper_bound where possible.

  • prefix and [start, stop) are intersected. start > stop raises ValueError; equal bounds produce an empty scan that still exposes the schema.

  • Keys are raw bytes (empty keys, embedded nulls, and 0xff bytes are all valid). The MVP assumes RocksDB’s default bytewise comparator and rejects custom comparators explicitly instead of mis-scanning them.

Results follow comparator order with no missing/duplicate records across batch boundaries. Iterator errors propagate (through the Arrow consumer as an error carrying the native message) and are never masked as clean end-of-stream.

Batch sizing

  • batch_size (default 65536): maximum rows per batch.

  • max_batch_bytes (default 8 MiB): maximum key+value payload plus offset overhead per batch. A single record larger than the cap raises a clear error; pass allow_overflow=True to emit it alone instead.

  • The schema uses int32 offsets for the whole stream. Records that would overflow int32 offsets fail explicitly; the schema never changes mid-stream.

These caps bound producer batch memory, not whole-process RSS: the block cache, pinned snapshot history, and consumer-retained batches are additional.

Snapshots

Every scan pins a consistent RocksDB read view when it is established, so concurrent writes cannot change what an open stream observes:

snap = db.create_snapshot()
a = db.scan_arrow(prefix=b"a/", snapshot=snap)
b = db.scan_arrow(prefix=b"b/", snapshot=snap)
snap.release()   # streams already hold the pinned view

Two streams sharing one snapshot observe the same horizon across intervening writes; separately created snapshots may see later data. The snapshot must belong to the same DB instance and must not be released while a scan that uses it is being created. Snapshot.sequence_number exposes the pinned read-view identity for integration checks. A scan created without an explicit snapshot pins its own view at creation time.

Column families

PyRocksDBExtended.scan_arrow_cf(cf_handle, ...) scans a named column family with the same contract. A snapshot created on the DB may be shared across column families so multi-relation consumers observe one horizon. Dropping a column family with an active scan on it is rejected; close the scan first.

TransactionDB

TransactionDB.scan_arrow(...) exposes the same native scan contract on transaction-capable databases. scan_arrow_cf(cf, ...) scans a named CF; create_snapshot() and new_iterator() are available as well. A scan observes committed state at its pinned snapshot: writes from still-open transactions are not visible and appear only after commit. A snapshot must belong to the same database instance, so snapshots cannot be shared between a TransactionDB and a plain PyRocksDB. Transaction-local read-your-writes stays on the Transaction handle (txn.get); merging uncommitted writes into a scan remains a follow-up.

TransactionDB opens all persisted column families on reopen and supports the same CF management and direct CF reads/writes as PyRocksDBExtended. Transactions support put_cf, get_cf and delete_cf, and CF put/delete operations in PyWriteBatch. Dropping a CF is conservatively rejected while any transaction is active, or while an Arrow scan uses it. Finish transactions and close streams before dropping their families.

Snapshot-consistent materialization

On PyRocksDB, PyRocksDBExtended and TransactionDB, get and multi_get accept the same snapshot= object used by scans. CF variants get_cf and multi_get_cf do too. This closes the read-horizon gap in an index-scan / point-materialization pipeline:

snap = db.create_snapshot()
try:
    with db.scan_arrow_cf(index_cf, prefix=b"p/", snapshot=snap) as scan:
        reader = pa.RecordBatchReader.from_stream(scan)
        for batch in reader:
            version_keys = batch.column("value").to_pylist()
            payloads = db.multi_get_cf(facts_cf, version_keys, snapshot=snap)
            # Decode/validate payloads in the application, not PyRex.
finally:
    snap.release()

multi_get / multi_get_cf call native RocksDB MultiGet, returning a Python list in input order. Duplicate keys are preserved; missing keys are None and empty values are b"". Empty inputs still validate the DB, CF and snapshot. Inputs must contain at most 65536 byte keys per call; results are materialized, not a streaming or byte-bounded Arrow API. An operational error raises rather than returning a partial result list. Foreign, released and DB-closed snapshots fail clearly.

Keep the snapshot alive through both scan and point reads. A RocksDB sequence number identifies a storage view, not an authenticated application-level temporal horizon. GestaltDB-like consumers still need their own visibility, exact evidence identity, payload decoding and term-encoding checks.

Column-family integration opportunities

For a future CF-backed consumer, a single snapshot can cover fact records, index locators, dictionaries and persisted derived generations. CF-specific compression/compaction settings can isolate different access patterns while transactions publish related CF writes atomically. These are architectural capabilities, not measured reasoning speedups. Do not create a CF per predicate without measuring its handle/memtable/compaction costs.

GestaltDB currently stores prefixed keys in the default family, so its current layout needs scan_arrow plus snapshot-consistent point reads, not a CF migration. Its NativeKeyScan adapter currently converts Arrow buffers to Python byte rows; CF support alone does not provide decoded columnar facts or zero-Python reasoning. Re-audit its capability matrix and adapters before enabling transactional/CF acceleration (GestaltDB issue #194).

Lifecycle and safety

  • Streams are single-consumer: __arrow_c_stream__ may be called exactly once (PyCapsule name arrow_array_stream per the Arrow PyCapsule standard). The capsule destructor releases stream state exactly once.

  • ArrowScan.close() (also a context manager) ends iteration early and releases the iterator and snapshot resources. Reading after close, or after database closure, fails instead of touching freed memory.

  • Closing the database invalidates active scans safely: exported batches remain valid (owned buffers), subsequent reads fail clearly.

  • ArrowScan.sequence_number reports the read view the scan observes.

  • Releasing an Arrow consumer closes the native scan even if an ArrowScan variable is retained. Explicit close and repeated release are idempotent.

Reading data back yields raw key/value binary columns. Decoding application payloads (JSON, MessagePack, term encodings, graph relations) stays with the caller; predicate filtering and graph semantics do not belong in PyRex.

Reference

  • PyRocksDB.scan_arrow(prefix=None, start=None, stop=None, batch_size=65536, max_batch_bytes=8388608, read_options=None, snapshot=None, allow_overflow=False) -> ArrowScan

  • PyRocksDBExtended.scan_arrow_cf(cf_handle, ...) — same keyword contract.

  • TransactionDB.scan_arrow(...) — same keyword contract on the default column family; observes committed state (open-transaction writes excluded).

  • TransactionDB.scan_arrow_cf(cf_handle, ...) — same contract across CFs.

  • get(key, read_options=None, snapshot=None) and multi_get(keys, read_options=None, snapshot=None)

  • get_cf(cf, key, read_options=None, snapshot=None) and multi_get_cf(cf, keys, read_options=None, snapshot=None)

  • PyRocksDB.create_snapshot() -> Snapshot (also on TransactionDB; snapshots are per-instance and never shared across DB objects)

  • Snapshot.release(), Snapshot.is_valid(), Snapshot.sequence_number

  • ArrowScan.close(), ArrowScan.is_closed, ArrowScan.sequence_number
